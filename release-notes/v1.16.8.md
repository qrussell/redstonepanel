Backups on another cluster member: a copy of each server's backups kept on a second machine, so a world survives losing the one it ran on.

## New

- **Also keep a copy on.** On a cluster master, open a server's **Backups** tab and choose another member to hold copies: the master, or another node. After each scheduled or manual backup the master copies it there and checks it arrived whole with SHA-256. A node's backup going to another node passes through the master; nodes never talk to each other.
- **Copies follow the server's Keep.** Scheduled copies are pruned to the same number as the server's own backups; manual copies stay until you delete them.
- **Download, Put back and Restore.** Copies are listed on the Backups tab. **Put back** (admins) copies one into the server's own backups, where **Restore** brings its world back.
- **Restore after losing a machine.** Make a new server of the same edition and version, open its **Backups** tab, click **Use a copy of another server's backup…**, then **Put back** and **Restore** the copy you want.
- **Alerts.** A failing copy (the member is off, or its disk is full) shows under **Needs attention** on the master's dashboard and sends the new **Backup copy to another member failed** webhook event (`backup_copy_failed`), once per run of failures. The master retries every few minutes and catches up on what it missed.

## Good to know

- The master does the copying, every 5 minutes and straight away after **Back up now**, so a scheduled backup's copy can arrive up to about 5 minutes after the backup. While the master is down nothing is copied; it catches up when it's back.
- Copies are stored in `/var/backups/redstonepanel/remote/<member>/<server>/` on the member holding them, readable only by root.
- Standalone panels don't have this yet. Copies to an SSH server or S3-compatible storage are planned for 1.16.11.

Tested: 16 new unit tests, and a master with two nodes in systemd containers (33 checks), including stopping a node and restoring its server's world from the copy on the other node.

## Upgrading an existing panel

Copies need **every cluster member on 1.16.8**; a node still on an older version says so when you pick it. Upgrade the nodes and the master, then turn copies on per server. Reload the panel in your browser after the upgrade. Nothing changes until you turn copies on.

## Installing

RedstonePanel runs on **Ubuntu 24.04 and 25.04**. The easiest way to install it, and to get every later version with `apt upgrade`, is the signed **qrussell-repo** apt repository:

```bash
sudo apt install -y curl ca-certificates
curl -fsSL https://qrussell.github.io/qrussell-repo/deb/qrussell-repo.gpg | sudo tee /usr/share/keyrings/qrussell-repo.gpg >/dev/null
echo "deb [signed-by=/usr/share/keyrings/qrussell-repo.gpg] https://qrussell.github.io/qrussell-repo/deb ./" | sudo tee /etc/apt/sources.list.d/qrussell.list
sudo apt update
sudo apt install redstonepanel
```

Or in one line: `curl -fsSL https://raw.githubusercontent.com/qrussell/redstonepanel/main/install.sh | sudo sh`

Then open **http://&lt;server&gt;:8080/** and sign in with a Linux account in the `sudo` group.

To check the repository key before trusting it, `gpg --show-keys /usr/share/keyrings/qrussell-repo.gpg` should show the fingerprint `9994A9EB39EB3C101C949FB2012BA14E0FE3A355`.

Prefer not to add a repository? Download `redstonepanel_1.16.8_all.deb` below and run `sudo apt install ./redstonepanel_1.16.8_all.deb`. You then install each new version the same way.

The [user manual](https://github.com/qrussell/redstonepanel/blob/main/docs/guide/README.md) walks through every feature, with screenshots.

## Upgrading

If you use the qrussell-repo repository:

```bash
sudo apt update && sudo apt upgrade
```

New versions reach the repository within a few hours of their release. Otherwise, install the new .deb as above.

Running servers keep running through the upgrade.
